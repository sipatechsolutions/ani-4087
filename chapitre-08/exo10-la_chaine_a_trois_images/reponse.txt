Le minimum d'images :
Je le deduis des conflits de resultat.txt :
- L = 0 : CONFLITS 1 0 0. Une image suffit.
- L = 1 : une image donne 5 conflits sur 6 (toutes les trames sauf la premiere), deux images en donnent 0.
- L = 2 : deux images donnent encore 4 conflits (de la trame 3 a la trame 6), trois images en donnent 0.
A chaque fois, les conflits disparaissent des que n = L + 1, jamais avant. La raison : la trame u peint l'image (u - 1) % n, qui avait ete soumise par la trame u - n. Elle est encore lue si u - n se trouve parmi les L trames d'avant, c'est-a-dire si n <= L. Il faut donc n > L, et le minimum d'images est n = L + 1 : une image pour peindre, plus une pour chaque trame pendant laquelle le compositeur garde la sienne. Les premieres trames y echappent seulement parce que les trames de numero 0 ou moins n'existent pas : c'est pour cela que CONFLITS 2 2 vaut 4 et non 6.

Sur le simulateur :
Sur le simulateur, le compositeur lit l'image apres le rendu, dans la meme trame, donc L = 0, et une seule image suffit deja (CONFLITS 1 0 0). Le cycle de trois images n'y apporte rien de visible : aucune trame n'etait en conflit avec une image, il n'y en a donc pas moins avec trois. En plus, dans NKXRDemo, il n'y a qu'une seule vraie cible par oeil : les trois index de la chaine designeraient la meme texture, et le cycle 0, 1, 2 ne serait qu'un numero. Dans ma salle, les trois images existent vraiment, mais leur seul effet est de tripler la memoire : 3 x 2,2 Mo par oeil (720 x 792 x 4 octets) au lieu de 2,2 Mo. Les trois images ne servent que sur un vrai casque, ou le compositeur garde l'image une ou deux trames pour la deformer et la reprojeter (L = 1 ou 2). La, le minimum L + 1 vaut 2 ou 3, et trois images evitent de peindre dans celle qu'il affiche. Le simulateur ne peut pas montrer ce gain : il cache le besoin, comme il cachait le mauvais index a l'exercice 8.
