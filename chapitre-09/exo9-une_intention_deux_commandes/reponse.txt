Ce qui change :
Sur un vrai casque, seule la table changerait : le type Table (usage -> commande) et la fonction lireTable() qui la remplit. Dans resultat.txt, la table 1 (souris : SOURIS_G, SOURIS_D, TAB) et la table 2 (clavier : ESPACE, E, TAB) donnent exactement les memes lignes d'images (2 tirer, 3 saisir, 5 menu) et IDENTIQUES OUI. Le programme n'a pas ete modifie entre les deux : seule la donnee lue a change. Sur un casque, cette table ne serait meme plus ecrite par l'application : c'est le pilote du casque, dans le backend, qui relie chaque usage a un organe reel (par exemple SELECT a la gachette droite), selon le materiel branche et les preferences de l'utilisateur. La declaration des actions et la fonction rejouer() resteraient identiques.

Aucun nom de bouton :
Hors de la table, le code ne manipule que des usages et des noms d'actions. La declaration lit "nom USAGE" ; rejouer() cherche table.find(actions[a].usage) puis regarde si la commande trouvee fait partie des commandes tenues (tenues.count(it->second)). Aucune chaine SOURIS_G, SOURIS_D, TAB, ESPACE ou E n'apparait dans correspondance.cpp : une recherche de ces mots dans le fichier ne trouve que "TABLE", le titre affiche. Toutes les commandes arrivent par l'entree, dans la table. C'est ce qui permet de passer de la souris au clavier sans toucher une ligne du code.

L'action inactive :
saisir_g (usage GRAB_LEFT) est inactive dans les deux tables, parce qu'aucune des deux ne donne de commande a GRAB_LEFT : le simulateur a souris ne l'a pas liee, et le clavier non plus. Une action inactive ne fait jamais d'appui : son active vaudrait 0 et son current resterait a 0, exactement comme un bouton jamais touche. Rien ne le signale de lui-meme ; sans la ligne INACTIVE saisir_g, on croirait que la main gauche fonctionne et que l'utilisateur n'a simplement jamais appuye. C'est pour cela qu'on journalise une fois, au demarrage, toutes les actions inactives : le jour ou une liaison manque, cette ligne donne la cause en une seconde.
